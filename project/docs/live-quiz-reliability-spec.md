# Live quiz reliability spec

This is the baseline for future live-quiz reliability work: it records current behaviour and known gaps only, without assigning a design to any gap.

1. **Joining — already true today (automated coverage: `JoinTests.test_join_returns_token`, `test_bad_pin_is_404`, `test_duplicate_nickname_rejected`):** a player who supplies an open game's six-digit PIN and an available nickname joins that game and sees “You're in”, while a player with no live matching game sees “No live game with that PIN.”
2. **Mid-game connection loss — gap (automated coverage: none):** when a player's state poll fails for any reason, that player sees “That's a wrap” and “Thanks for playing.”, so temporary connection loss is not distinguished from a game that is actually unavailable and no retry or resume behaviour is specified.
3. **Answering at the edges — already true today (automated coverage: `GameplayTests.test_cannot_answer_twice`, `test_cannot_answer_before_start`, and `test_foreign_choice_rejected`):** the server accepts at most one valid answer while the question is live and rejects an edge-case attempt with “No question is accepting answers right now.”, “Time's up for this question.”, “You have already answered this question.”, or “That answer is not an option on this question.”, which the submitting player receives.
4. **The host's device dying — gap (automated coverage: none):** when the host device disconnects or closes, the server leaves the game in its current state and players continue to see that state until a host returns or an operator ends it, with no host-recovery message or takeover rule specified.
5. **Abandonment — gap (automated coverage: none):** when a player stops polling or leaves without submitting, the game retains that player and the host continues to see the player in the room or standings, with no timeout, removal, or absence indication specified for either audience.
6. **Two games in one room — already true today (automated coverage: `HostingTests.test_session_is_tenant_scoped` plus the unique live-PIN allocation path):** each player token is checked against its PIN and each host session is tenant-scoped, so a player or teacher sees only the game identified by their own PIN or session rather than another game's state.
7. **The whole class answering at once — gap (automated coverage: none):** simultaneous submissions have no documented capacity or contention guarantee, although each player can only create one answer per question, so neither the host nor players are promised what happens if the room overloads the service.
8. **Fairness — already true today (automated coverage: `GameplayTests.test_question_never_leaks_correct_answer`, `test_score_stays_hidden_until_reveal`, `test_speed_bonus_rewards_faster_answers`, and `test_streak_adds_bonus`):** players cannot see correct choices or score changes before reveal, and the server—not the player device—measures response time and applies the same speed and streak rules for everyone.
